Why Cardscape

Five reasons a team picks a self-hostable kanban over a hosted one, and the one reason to pick Cardscape over every other self-hostable kanban.

1 · Self-hostable, you own the data

One docker compose up and the whole thing is on your hardware. No vendor can read your boards, change the rules, or sunset the product.

2 · AI integration that is not bolted on

A first-party MCP server is a peer to the REST API. The same domain model, the same authorization, the same idempotency. An AI client drives the boards through the same Application layer a human does through the web UI.

3 · Multi-database without lock-in

SQLite for solo and dev, PostgreSQL or MariaDB for production. The provider is configuration, not code.

4 · A complete feature surface

Workspaces, boards, lists, cards, members, comments, checklists, attachments, calendar, automation, extensions, Inbox, Planner, API tokens, audit logs. Designed for the long run, not a demo.

5 · Modern .NET, end to end

ASP.NET Core 11, Blazor WebAssembly, Entity Framework Core 10 LTS, Radzen.Blazor. Type-safe, fast, long-term support.

The differentiator

The MCP server is the headline. Every other self-hostable kanban makes you write a glue layer between your AI client and your boards. Cardscape ships the glue.

The MCP server

The Model Context Protocol (MCP) is the open standard for "AI agent ↔ external tool" in 2025–2026. Cardscape ships a first-party MCP server in src/Cardscape.Mcp/.

What it does

  • Lets an AI client read boards, lists, cards, comments, members.
  • Lets an AI client create, update, move, and archive cards.
  • Lets an AI client add comments, assign members, set due dates, add labels.
  • Lets an AI client search across all boards.
  • Subscribes to board and card resources for live updates.

How it does it

  • Same Application layer the REST API uses.
  • Same MediatR pipeline. Same FluentValidation. Same Result<T>.
  • Bearer-token authentication via the same Members context.
  • Idempotency key on every write — safe retries for AI agents.
  • OpenTelemetry traces end-to-end: MCP call → handler → repository → DB.

Example tool calls

// 1. Show every card assigned to me that is due this week
cards_due_this_week({ assignee: "me" })

// 2. Create a card on the Q3 Roadmap board, in Doing, assigned to me
cards_create({
  board_id: "q3-roadmap",
  list_id: "doing",
  title: "Investigate the flaky integration test",
  assignee_ids: ["me"]
})

// 3. Move every card with the "urgent" label to Done
cards_move_by_label({
  label: "urgent",
  to_list_id: "done"
})

// 4. Run the Monday triage prompt against the Inbox
prompts_run({
  name: "triage-inbox"
})

Get started

Today, the application is a scaffold — there is no runnable product yet. The honest quickstart is the developer one: 

git clone https://github.com/cardscape/cardscape.git
cd cardscape
dotnet build                       # 11/11 projects, 0 errors, 0 warnings
dotnet test                        # green by default (no domain yet)

The first runnable self-hostable build, with a demo workspace, seeded data, and docker compose up to go, ships with the v0.1.0-mvp tag at the end of Phase 1.

To follow along: watch the GitHub releases and read the implementation plan.
