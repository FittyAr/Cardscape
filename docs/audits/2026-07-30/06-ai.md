- **Gaps (what is missing or drifted)**:

     `docs/roadmap/03-execution-plan-v1.1.0.md:461-463` says "on every
     card `DueDate` change, push the event to the user's Google
     Calendar". `IGoogleCalendarSyncService.PushCardDueDateAsync`
     exists in `HttpGoogleCalendarSyncService.cs:32`, but `grep` for
     `PushCardDueDateAsync` across the entire `src/` tree returns
     only the implementation file and the interface — no domain
     event handler, no Wolverine consumer, no API endpoint, no UI
     trigger. The sync engine is built but never called.
  2. **Pull on calendar webhook is stubbed.**
     `HttpGoogleCalendarSyncService.PullCalendarChangesAsync` at
     `src/Cardscape.Infrastructure/Integrations/HttpGoogleCalendarSyncService.cs:99-116`
     returns `Result.Success(0)` and the inline comment (lines 109-113)
     explicitly says: *"The actual pull logic walks the events list
     and updates card.dueDate for each event whose id matches a
     stored GoogleCalendarEventId. The implementation is a future
     PR — for v1.1.0 the round-trip from Google to Cardscape is
     documented but stubbed."*
  3. **No calendar-webhook endpoint.** The plan says "on calendar
     webhook, update the card", but `MapGoogleCalendarEndpoints`
     (`GoogleCalendarEndpoints.cs:15-58`) only exposes `POST /connect`,
     `GET /`, `DELETE /`. There is no `POST /webhook` / `/notify`
     handler. `grep` for `webhook` or `WatchCalendarAsync` callers
     across `src/` confirms no consumer exists.
  4. **Web UI "Connect" button is a placeholder.** The Blazor page
     calls `GoogleCalendarApiClient.ConnectAsync` at
     `src/Cardscape.Web/Services/Api/GoogleCalendarApiClient.cs:21-34`,
     but the request body is a hard-coded placeholder
     (`workspaceId = Guid.Empty, googleEmail = "ui-placeholder@local",
     encryptedRefreshToken = "ui-placeholder"`). The inline comment
     (lines 23-28) explicitly says: *"The v1.1.0 UI is a placeholder:
     in production the browser would redirect to Google's OAuth
     consent screen, exchange the auth code, and post the encrypted
     refresh token."* So the OAuth flow itself is NOT implemented
     end-to-end in the UI.
  5. **No tests for the bounded context.** `grep` for
     `GoogleCalendar` / `HttpGoogleCalendarSyncService` /
     `GoogleCalendarConnectionRepository` across `tests/` returns
     zero matches (`tests/Cardscape.IntegrationTests/Endpoints/CalendarQueryTests.cs`
     is for the in-app calendar query, not Google Calendar).
  6. **`ISecretProtector` usage is correct** but the
     `EncryptedRefreshToken` field is encrypted at the API boundary
     (the endpoint accepts it already encrypted, see
     `GoogleCalendarEndpoints.cs:21-23`), and decrypted inside
     `GetAccessTokenAsync` at line 171. This is the right shape but
     means there is no real OAuth code-exchange step anywhere in
     the codebase — the API trusts the client to have already done
     it.

- **Notes**:
  - The bounded context is a textbook vertical slice: aggregate →
    events → repository → handlers → REST → Web UI. The plumbing
    is solid.
  - The gaps above are all in the *behaviour* layer (the actual sync
    trigger, the webhook, the OAuth exchange, the tests). No code is
    broken; the feature just doesn't sync anything end-to-end.
  - If the goal of v1.1.0 is to ship the *plumbing* and document the
    sync engine as a follow-up, the current shape is reasonable. If
    the goal is "Google Calendar actually pushes events on a due-date
    change today", this is a real gap.

## 4.10 MCP AI tools

- **Verdict**: **DONE** (with a small drift on the error-handling shape)
- **Plan bullets** (`docs/roadmap/03-execution-plan-v1.1.0.md:514-525`):
  - `ai_generate_card_description(cardId)` — wraps
    `GenerateCardDescriptionCommand`.
  - `ai_summarize_thread(commentIds)` — wraps
    `SummarizeCommentThreadCommand`.
  - `ai_make_checklist(cardId)` — wraps
    `GenerateChecklistFromDescriptionCommand`.
  - `ai_suggest_owners(cardId)` — wraps
    `SuggestCardOwnersCommand`.
  - Tools fail gracefully when `IAiService` is the rule-based
    provider, returning an "AI not configured" error code.

- **Evidence**:
  - All four tools in `src/Cardscape.Mcp/Tools/AiTools.cs:14-74`:
    - `ai_generate_card_description` (attribute `Name = "ai_generate_card_description"`,
      line 17) — wraps
      `AiFeatures.GenerateCardDescriptionCommand(cardId, extraContext)`
      (line 26). Span: `McpToolSpan.Begin("ai_generate_card_description")`
      (line 23).
    - `ai_summarize_thread` (line 32) — wraps
      `AiFeatures.SummarizeCommentThreadCommand(commentIds)` (line
      40). Comment ids are passed as `Guid[]` (line 34), matching
      the plan's `(commentIds)` shape.
    - `ai_make_checklist` (line 46) — wraps
      `AiFeatures.GenerateChecklistFromDescriptionCommand(cardId)`
      (line 54).
    - `ai_suggest_owners` (line 60) — wraps
      `AiFeatures.SuggestCardOwnersCommand(cardId, maxSuggestions)`
      (line 69). Accepts an optional `maxSuggestions = 3` (line
      63) which is a small extension on the plan's `(cardId)`
      shape.
  - Every tool uses the same pattern (lines 24-30, 38-44, 52-58,
    67-73):
    1. Open a span via `McpToolSpan.Begin(...)` for tracing.
    2. Resolve the Wolverine bus from `McpToolContext.Bus`.
    3. Invoke the corresponding command and await the
       `Result<T>`.
    4. On success, return the unwrapped value; on failure, throw
       `InvalidOperationException(result.Error.Message)`.
  - All four commands resolved in the tools are the same records
    used by the REST endpoints (§4.9) and the Web UI buttons
    (`AiFeatures.cs:22-34`), so the MCP and REST surfaces share
    a single command/query bus entry point.

- **Drift**:
  - The plan says the tools should "fail gracefully when
    `IAiService` is the rule-based provider (return an 'AI not
    configured' error code the AI client can surface to the
    user)". The actual behavior is the opposite of "fail":
    the rule-based provider (`RuleBasedAiService.cs:21-106`)
    always returns a successful `Result` with a canned
    response for `describe-card`, `summarize-thread`,
    `make-checklist`, and `suggest-owners` (lines 67, 71, 87,
    98). The four MCP tools therefore *succeed* against the
    rule-based provider; they never reach the throw branch
    (line 29 of `AiTools.cs`) for a "real" `IAiService`
    call. This is arguably better than the plan's
    "fail with an error code" — the user always gets a
    useful response — but it does mean the "AI not configured"
    error code is never produced in practice.
  - The error path the tools *do* take is when the underlying
    `Result.Failure` comes from the handler itself (e.g. card
    not found, empty comment list, etc., see
    `AiFeatures.cs:57-59`, `90-93`, `106-109`, `133-136`,
    `172-175`, `179-182`, `186-189`). The tool surfaces
    those as `InvalidOperationException` with the
    `DomainError.Message` (line 29 of `AiTools.cs`). The
    `DomainError.Code` (e.g. `card.not_found`,
    `comments.empty`) is not propagated to the MCP client;
    only the human-readable message is. A strict reading of
    the plan would want the error code surfaced as well,
    so an AI client could branch on it.

- **Notes**:
  - All four tool names match the plan's exact spelling
    (`ai_generate_card_description`, `ai_summarize_thread`,
    `ai_make_checklist`, `ai_suggest_owners`).
  - The tools are decorated with `[McpServerToolType]` on the
    class (line 14) and `[McpServerTool(Name = "...")]` on each
    method (lines 17, 32, 46, 60), so the MCP SDK auto-registers
    them.

### Most important gap

The single most important gap is the missing **"Make checklist" and
"Smart assign" ✨ buttons in the Web UI** (§4.9). The plan explicitly
calls them out as four user-facing buttons in `CardDetail.razor`; the
backend pipeline (commands, handlers, REST endpoints, `IAiApiClient`)
is complete and tested-by-construction, but the UI surface only
exposes two of the four. Closing this gap is a 2-button + 2-handler
change in `CardDetail.razor` and would complete §4.9 to a full DONE
without any backend work.

A close second is **§4.6's unwired sync** (`PushCardDueDateAsync` is
never called on a `DueDate` change and `PullCalendarChangesAsync` is
stubbed). This is a much larger change — it needs a domain event
handler in the application layer, a real Google OAuth flow, a
webhook endpoint, and a real calendar-event id mapping — but the
plumbing is all there, so the change is well-scoped.
