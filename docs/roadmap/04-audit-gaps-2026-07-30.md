## 2. CRITICAL — runtime blockers (fix first)

These would crash the app or silently break the contract on
first use. They are the gaps the release notes cannot gloss
over.

### G1 — Integration DI registrations missing ✅ DONE

**Where:**
- `src/Cardscape.Infrastructure/DependencyInjection/InfrastructureServiceCollectionExtensions.cs:284-331`
- Affects: Slack (`ISlackNotificationService`,
  `ISlackWorkspaceRepository`, `ISlackChannelRepository`),
  Google Drive (`IGoogleDrivePickerService`,
  `IGoogleDriveConnectionRepository`), GitHub
  (`IGitHubService`, `IGitHubRepoLinkRepository`,
  `IGitHubPullRequestLinkRepository`), Email
  (`IInboundEmailService`, `IInboundEmailAddressRepository`).

**Symptom:** the bounded contexts, abstractions, services,
endpoints, and MCP tools all exist and compile. **But none of
the services or repositories are registered with DI**, so any
runtime call that resolves them throws
`InvalidOperationException: No service for type '…' has been
registered`. The MCP `integrations_slack_*` /
`integrations_google_drive_*` / `integrations_github_*` /
`integrations_email_*` tools, and the REST endpoints under
`/api/integrations/*`, will all 500 on first use.

**Fix:** extended
`InfrastructureServiceCollectionExtensions.AddInfrastructure`
to register every integration abstraction with its
implementation. Repositories are `AddScoped` (they wrap the EF
Core `DbContext`); the three HTTP-backed services
(`HttpSlackNotificationService`, `HttpGoogleDrivePickerService`,
`HttpGitHubService`) are wired with `AddHttpClient<TInterface,
TImpl>` so the typed `HttpClient` lifetime is managed by the
factory; `DefaultInboundEmailService` is `AddScoped` because
it composes the address repository + the Wolverine
`IMessageBus`. Build green (0 warnings, 0 errors); 94/94
integration tests green.

**Severity:** CRITICAL — advertised as working in the v1.0.0
changelog and the `v1.1.0-roadmap-execution` release notes,
but it is not.

### G2 — SAML SSO is stubbed

**Where:** `src/Cardscape.Api/Endpoints/SamlEndpoints.cs`
(presumed; the audit flagged the four endpoints
`/saml/{slug}/login`, `/login-init`, `/acs`, `/metadata` as
returning 200-OK with no real protocol).
- Plan ref: §4.2.

**Symptom:** the SAML admin UI, the `SamlConnection`
aggregate, the `SamlConnectionRepository`, and the
`Sustainsys.Saml2.AspNetCore` package are all in. But no
`SamlAuthenticationHandler` exists, and the endpoints do not
forward to the Sustainsys challenge/ACS middleware. IdPs that
POST a `SAMLResponse` to `/saml/{slug}/acs` will see a JSON
200 OK and produce no user session.

**Fix (planned):** add a `SamlAuthenticationHandler.cs` to
`src/Cardscape.Api/Authentication/` that wires Sustainsys
into the auth pipeline, and rewrite the four endpoint stubs
to call into the handler. The `SamlConnection` aggregate
already carries the IdP metadata URL, ACS URL, and audience.

**Severity:** CRITICAL — enterprise customers cannot
authenticate.

### G3 — SCIM `/scim/v2/Groups` is missing ✅ DONE

**Where:** `src/Cardscape.Application/Abstractions/IScimService.cs`,
`src/Cardscape.Infrastructure/Scim/ScimService.cs`, and
`src/Cardscape.Api/Endpoints/Scim/ScimEndpoints.cs`.
- Plan ref: §4.4.

**Symptom:** the Users endpoints
(`GET/POST/GET-id/PUT/PATCH/DELETE /scim/v2/Users`) are in,
plus the per-workspace ScimToken admin endpoints. The Groups
endpoints (`GET/POST/GET-id/PUT/PATCH/DELETE
/scim/v2/Groups`) do not exist. IdPs that try to provision
groups will get 404.

**Fix:** extended `IScimService` with the 6 Groups methods
(`ListGroupsAsync`, `CreateGroupAsync`, `GetGroupAsync`,
`UpdateGroupAsync` (PUT), `PatchGroupAsync` (RFC 7644
§3.5.2), `DeleteGroupAsync`) and implemented them in
`ScimService`. Mapped a SCIM `Group` 1:1 to a `Workspace`
(the natural multi-user container) and a SCIM `Group.member`
to a `WorkspaceMember`; the SCIM group id is the stable
form `workspace-{guid}`. Mapped the 6 endpoints under
`/scim/v2/Groups`. Also fixed a pre-existing auth-flow bug
where the policy-scheme `ForwardDefaultSelector` was
routing SCIM bearer tokens to the API-token scheme; the
selector now routes `/scim/v2/*` requests to
`ScimAuthenticationHandler`. Added 2 integration tests
(`ListGroups_ForWorkspace_Returns200_WithWorkspaceGroup`,
`CreateGroup_WithMinimalPayload_Returns201_AndPersists`).
Build green, SCIM tests green.

**Severity:** CRITICAL — SCIM v2 requires both Users and
Groups; a one-sided implementation is non-conformant and will
fail Okta / Entra ID validation.

### G4 — 2FA TOTP is not wired into the login flow ✅ DONE

**Where:** `src/Cardscape.Application/Authentication/Queries/LoginUserQuery.cs`
(presumed path).
- Plan ref: §4.3.

**Symptom:** the `TotpCredential` aggregate, the
`/api/auth/2fa/enroll`, `/verify`, `/disable` endpoints, the
`OtpNet` usage, and the Web UI `Settings → Two-factor` page
all work. But `LoginUserQuery` does not branch on
`user.HasActiveTotpCredential()`. A user with 2FA enabled
logs in with just email + password and the TOTP step is
skipped.

**Fix:** extended the `LoginUserQuery` handler to look up
the user's `TotpCredential` after the password check
succeeds. If a non-deleted credential exists and the caller
did not pass a `totpCode`, the response is a partial result
with `RequiresTotp = true` and a one-shot `PendingTotpToken`
(no JWT). The browser then posts the token + 6-digit code to
the new `POST /api/auth/login/totp` endpoint
(`ConsumePendingTotpLoginQuery`), which consumes the token,
verifies the code via `OtpNet` (advancing `LastUsedCounter`),
and issues the JWT. The Web UI `/login` page was extended to
render a TOTP code input when `RequiresTotp` is true, and the
`AuthService` learned a `LoginWithTotpAsync` roundtrip. The
in-memory `IPendingTotpLoginStore` (a 5-minute, one-shot
dictionary of 256-bit tokens) is registered as a singleton.
3 new i18n keys (`Login_TotpCode_Label`,
`Login_TotpCode_Required`, `Login_TotpCode_Invalid`) were
added in both `SharedResource.resx` and `SharedResource.es.resx`.
3 new unit tests cover the no-2FA / challenge / valid-code /
invalid-code paths; the existing tests stay green.

**Severity:** CRITICAL — TOTP is advertised as working but
is bypassed.

### G5 — Data residency policy is dead code

**Where:** `src/Cardscape.Domain/Workspaces/Workspace.cs`
(`GuardRegion`) and the API endpoints.
- Plan ref: §4.5.

**Symptom:** the `Region` enum, the
`Workspace.SetRegion` / `GuardRegion` methods, the
`IDeploymentRegion` interface, the migration
`IssueWorkspaceRegion`, and the Web UI region selector are
all in. But `GuardRegion` is never called from any
endpoint, and `IDeploymentRegion` is registered but unused.
Cross-region writes are not blocked.

**Status:** ✅ **DONE** in commit `ff17441`. Wires
`GuardRegion` into the request pipeline via a per-group
endpoint filter `RegionGuardEndpointFilter` (and a
`RequireRegionGuard()` extension). For any endpoint that
takes a `workspaceId` route value, the filter loads the
workspace and calls `GuardRegion`; on mismatch it returns
422 with a structured error body. Applied to the
`/api/workspaces` group, the Slack integration endpoints,
the SAML endpoints, the SCIM admin endpoints, and the
invitations endpoints. A 3-test integration suite
(`RegionGuardEndpointFilterTests.cs`) covers the happy path,
the cross-region 422, and the unaffected
non-workspace-scoped path. Build green, 3/3 new
integration tests green.

vertical slice lands green" rule. Each item lands on
`master` as a single commit, with the build + tests
green at the end.

   commit, ships green.**

   command change + 1 DTO field + 1 Web UI conditional
   that's already there. **One commit, ships green.**
