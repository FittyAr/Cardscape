# Plan de modernización integral de Cardscape

> **Estado**: En ejecución  
> **Inicio**: 2026-08-11  
> **Stack objetivo**: .NET 10, ASP.NET Core 10, Blazor WebAssembly 10, EF Core 10 y Radzen.Blazor  
> **Rama de entrega**: `master` (rama principal real del repositorio; `origin/HEAD` apunta a `origin/master`)  
> **Compatibilidad**: no se preservará compatibilidad hacia atrás mientras el producto no esté en producción.

## 1. Objetivo y reglas de decisión

El objetivo es llevar todo el repositorio a un estándar profesional, verificable y mantenible. La revisión cubre arquitectura, dominio, casos de uso, persistencia, API, MCP, Blazor, seguridad, observabilidad, pruebas, automatización y documentación.

Reglas permanentes:

- Favorecer APIs y patrones modernos soportados por .NET 10; no introducir previews ni actualizar `global.json` sin autorización explícita.
- Mantener Clean Architecture sólo donde los límites aporten independencia real. Eliminar abstracciones, service locators y capas ceremoniales que no protejan una frontera.
- Organizar Application/API/Web por capacidad o bounded context y evitar archivos monolíticos.
- Desarrollar y ejecutar la suite ordinaria sobre SQLite, manteniendo compatibilidad de release comprobada con PostgreSQL y MySQL.
- No anunciar MariaDB ni publicar una release que lo incluya hasta que un provider EF Core 10 estable supere migraciones e integración sobre MariaDB real. Una declaración de compatibilidad sin matriz verde no satisface este gate.
- Usar exclusivamente componentes Radzen en la UI. CSS isolation se acepta sólo para interacciones sin equivalente Radzen, como un kanban; cualquier otra excepción deberá quedar justificada.
- No mantener rutas, contratos, migraciones o adaptadores obsoletos por compatibilidad. Los cambios incompatibles deben actualizar en el mismo bloque código, pruebas y documentación.
- Cada bloque termina con build Release sin warnings, pruebas pertinentes verdes, actualización de este checklist, commit pequeño y push a `origin/master`.

### Fase 2 — Superficies críticas

- [ ] Autenticación/autorización: JWT, API tokens, OAuth/OIDC, SAML, SCIM, 2FA, políticas y aislamiento multi-tenant. La autorización admin falla cerrada, la administración SAML completa es owner-only y la inspección de dead letters operativos dejó de estar disponible para cualquier usuario autenticado: exige `AdminOnly`. La sesión refresh ficticia fue eliminada y `exp` es la única expiración JWT. Google, Microsoft y Apple usan correlación protegida más cookie externa efímera; el callback Web espera la persistencia cookie-backed del token antes de notificar autenticación y forzar navegación, eliminando la carrera de la primera petición. SCIM está aislado por owner/workspace tanto en administración de tokens como en cada recurso User, sin lookups globales por id; `RequireTwoFactor` bloquea JWT y sólo acepta credenciales TOTP confirmadas. Login verifica la política 2FA de los workspaces con un `AnyAsync` EF Core y ya no materializa agregados/membresías en el camino crítico. El uso concurrente de un API token registra `LastUsedAt` mediante `ExecuteUpdateAsync` atómico y ya no puede convertir un handshake MCP válido en 500 por `RowVersion`. El enrolamiento queda pendiente hasta probar el autenticador; Slack valida owner/workspace y GitHub exige un enlace repo-board activo para toda lectura o escritura externa. La descarga de metadata SAML revalida SSRF, no sigue redirects, tiene timeout y límite de 1 MiB; se eliminó el acceso `file://` inalcanzable. Quedan los invariantes multi-tenant restantes.
- [x] Persistencia: modelo EF, transacciones, concurrencia, índices, consultas N+1, tracking y compatibilidad de los tres providers. Todos los repositorios, la exportación personal y el wipe del Seeder filtran, ordenan, paginan, agregan o eliminan mediante LINQ/EF Core; mirrors eliminó N+1 y las mutaciones masivas usan `ExecuteUpdateAsync`/`ExecuteDeleteAsync`. No queda SQL manual en `src`. Los índices siguen sus filtros/órdenes reales y se retiraron prefijos redundantes. El modelo común permite tipos nativos por provider. `RowVersion` es una convención única; el interceptor evita dobles incrementos, encola cada evento/broadcaster en la misma transacción EF y sólo limpia eventos después de commit exitoso. Las carreras de unicidad se clasifican por códigos nativos SQLite/PostgreSQL/MySQL; no quedan catches generales de `DbUpdateException`. SQLite limita al cliente únicamente comparaciones `DateTimeOffset` que no traduce, tras un filtro EF acotado. Los tres assemblies de migración compilan y CI aplica PostgreSQL/MySQL además de la suite SQLite.
- [ ] Gestión de secretos, cifrado, datos personales, borrado/anominización y retención. Webhooks y Slack ya persisten ciphertext con Data Protection; Slack dejó de ignorar el token por workspace y eliminó el fallback global multi-tenant incorrecto. Las invitaciones ya no envían el token a un transporte de email simulado que lo registraba en logs; la UI mantiene entrega manual de una sola visualización. OAuth Apps persiste el prefijo público real de ocho caracteres junto al hash SHA-256, nunca el secreto completo; alta y listado ya no muestran identificadores inconsistentes. Los logs ya no incluyen claves de idempotencia, prefijos de tokens SCIM, URLs de webhooks ni cuerpos/respuestas externas. Se retiró el relay CLEF experimental del navegador: no podía autenticar de forma real al cliente y promovía mensajes y propiedades arbitrarias con posible PII a telemetría confiable del servidor.
- [ ] Webhooks, importaciones, adjuntos y clientes HTTP: SSRF, validación, límites, reintentos, timeouts e idempotencia. Google Calendar ya no anuncia watch/webhook/pull ficticios; conserva únicamente el push saliente. Sus clientes OAuth/Calendar no siguen redirects, tienen timeouts y límites de respuesta, no reflejan cuerpos del proveedor y conservan el mapping card-event por conexión para ejecutar POST/PUT/DELETE reales. Las respuestas create/update/delete se disponen, el cuerpo exitoso queda limitado a 1 MiB y los errores ya no reflejan hasta 4 KiB arbitrarios de Google hacia el dominio/usuario. Google Drive fue eliminado por completo. Las rutas jerárquicas de adjuntos y webhooks ya exigen coincidencia entre URL y recurso persistido. Kanban separa preview/apply explícitamente, mantiene paridad de resumen y conserva asociaciones card-label; su lector aplica el límite de 10 MiB durante la lectura de streams no seekable, acepta exactamente el máximo y no refleja detalles internos de `JsonException`. Los webhooks protegen el secreto de firma con Data Protection, firman con el secreto real, no revelan prefijos derivados, no siguen redirecciones y ya no leen, persisten ni registran cuerpos de error externos; los fallos quedan reducidos a tipo seguro y estado HTTP. `ApiClientBase` ahora asume y libera explícitamente cada `HttpResponseMessage` después de consumir éxito/error; auth, descargas, borrado, recuperación de contraseña e importación cubren también sus caminos personalizados, evitando agotar recursos del handler en sesiones Web largas.
- [ ] Wolverine/background jobs: scopes, retries, outbox/inbox, cancelación y consistencia de eventos. Claim multi-worker ya es atómico. Los eventos de dominio ahora crean en la misma transacción una entrega outbox por broadcaster; leases EF Core evitan doble claim, los fallos se aíslan y reintentan con backoff, y un hosted dispatcher recupera commits interrumpidos. El Seeder dejó de lanzar `Task.Run` anidados desde endpoints: una cola bounded singleton acepta atómicamente una sola operación, un `BackgroundService` la ejecuta con el token de shutdown y observa/registra fallos mediante `LoggerMessage`. Los 25 scopes creados dentro de flujos async —outbox, sweepers, jobs, Seeder, validación JWT y broadcasters— usan `CreateAsyncScope`/`await using`, por lo que `DbContext` y cualquier dependencia `IAsyncDisposable` se liberan correctamente. Continúan inbox para mensajes externos y la auditoría integral de cancelación.
- [x] MCP: autorización equivalente a REST, lifetimes, transporte, suscripciones e idempotencia. Scopes, lifetime/composición, Streamable HTTP autenticado, aislamiento de suscripciones y reservas idempotentes cross-process verificados.
- [x] Observabilidad: logs estructurados, correlación, trazas, métricas, health checks y ausencia de PII/secrets. Se eliminó el `DatabaseLogSink` placeholder que descartaba eventos; sólo se anuncian console, rolling JSON y OTLP funcionales. Los seis assemblies que emiten logs —Application, Infrastructure, Web, API, MCP y Seeder— usan exclusivamente 121 contratos tipados generados con `[LoggerMessage]`, con IDs estables, niveles fijos o dinámicos explícitos, excepciones, value objects y propiedades estructuradas. El relay CLEF experimental y su paquete prerelease fueron eliminados: el servidor ya no confía ni almacena texto o propiedades arbitrarias del navegador. `App.razor` también dejó de escribir excepciones en `Console.Error`; el único uso directo restante de stderr pertenece al sink Serilog que implementa ese transporte. `CA1848` está activa globalmente y el rebuild completo confirma que no quedan llamadas directas a `LoggerExtensions.Log*`. API y MCP instrumentan ASP.NET Core y `HttpClient` con trazas/métricas OpenTelemetry y exportación OTLP opcional; Serilog enriquece los logs con el span correlacionado. `/health/live` comprueba únicamente el proceso y `/health/ready` verifica la base configurada con `Database.CanConnectAsync`; el endpoint sintético `/health` fue eliminado junto con todos sus consumidores.
