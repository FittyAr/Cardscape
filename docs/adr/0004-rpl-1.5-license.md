# ADR 0004: Reciprocal Public License 1.5 (RPL-1.5) for the project licence

- **Status**: Accepted
- **Date**: 2026-07-29
- **Deciders**: Cardscape maintainers

## Context

Cardscape is a public, open-source project. The licence
choice is a long-term one — every line of code, every
container image, every NuGet package that ships under
the project's name inherits it.

The two main candidate licences for a project of this
shape (open-source, self-hostable, B2B-friendly) are
MIT/Apache 2.0 and the **Reciprocal Public License
1.5 (RPL-1.5)**.

| Licence | Copyleft | Commercial-friendly | "Improvements stay open" guarantee |
|---|---|---|---|
| MIT / BSD / Apache 2.0 | ❌ permissive (no copyleft) | ✅ yes | ❌ no — a closed fork is permitted |
| AGPL-3.0 | ✅ strong copyleft | ❌ no (network use triggers source-disclosure) | ✅ yes |
| SSPL (Mongo) | ✅ "service-side" copyleft | ❌ controversial, OSI-rejected | ✅ yes |
| **RPL-1.5** | ✅ weak copyleft | ✅ yes (no network clause) | ✅ yes |

The maintainer's intent, declared in the README and the
project pitch, is:

> *"If you distribute a modified version, your
> modifications must also be RPL-1.5. This is
> deliberate — Cardscape is built in the open, and
> improvements must stay in the open."*

That intent rules out the permissive licences (a
proprietary fork is a possibility the maintainer wants
to foreclose) and the AGPL (which is hostile to SaaS
adoption — a hosted Cardscape-as-a-Service offering
would either be illegal or require a commercial
exemption, neither of which the maintainer wants to
mediate).

## Decision

Cardscape is licensed under the **Reciprocal Public
License 1.5 (RPL-1.5)**. The full text is in the
`LICENSE` file at the repository root. Every published
NuGet package and container image inherits the licence
through `<PackageLicenseExpression>RPL-1.5</PackageLicenseExpression>`
in `Directory.Build.props`.

RPL-1.5 is OSI-approved. It is the same licence family
used by the Boundless / OSGeo stack, the Red Hat
JBoss ecosystem, and several other open-source
infrastructure projects.

## Consequences

Positive:

- **Improvements stay open.** A company that adopts
  Cardscape and ships a modified version must publish
  the modifications under RPL-1.5. The maintainer does
  not have to mediate a "proprietary fork" risk.
- **Commercial-friendly.** Unlike AGPL, RPL-1.5 does
  not trigger source-disclosure for network use. A
  hosted SaaS that does not distribute a binary
  modified version is not bound by the copyleft. This
  is the licence's main commercial differentiator.
- **OSI-approved.** The licence is on the OSI list,
  which most enterprise procurement teams check.
- **Clarity for self-hosters.** The "if you fork, you
  must open the fork" rule is unambiguous and easy to
  explain in a procurement review.

Negative / accepted:

- **RPL is not as well-known as MIT or Apache.** New
  contributors may not immediately understand the
  "reciprocal" clause. The README and the CONTRIBUTING
  guide explain it in plain language; the maintainer
  commits to explaining it in every new-contributor
  conversation.
- **Some procurement teams have a "no copyleft" rule.**
  Cardscape is not a fit for those organisations.
  The maintainer accepts this as a feature, not a bug:
  Cardscape is for teams that want to be part of an open
  ecosystem, not for teams that want to keep a fork
  closed.

## When to revisit

This ADR should be revisited when **any** of the following
is true:

1. RPL-1.5 is updated to a new revision (RPL-2.0 etc.).
2. The Open Source Initiative delists RPL-1.5.
3. A pattern of contributors confused by the licence
   suggests the project's "improvements stay open"
   intent would be better served by a different
   licence (e.g. AGPL with a commercial-exemption
   programme).
4. The project relicences — a deliberate, maintainer-
   driven decision to change the licence, requiring
   contributor agreement and a major version bump.

Until one of those happens, the licence stays as-is.
